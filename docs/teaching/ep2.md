# 會自我檢查的自動化：用 AI 協作打造一條 PDCA 資料管線
## 以資安情資蒐集為例｜第 2 集（Do）：第一天，系統長出來了，但還不能信

> 形式：對話式圖文｜時間：民國 115 年（2026 年）11 月 26 日傍晚
> 角色：**Allan 講師**／**阿拉蕾**（AI 小助理）
> 圖示標記：【表情：…】對應角色設定圖；【畫面：…】為配圖說明

---

### 本集你會看到

- 新系統長什麼樣子（不講程式，只講流程）
- AI 坦白的第一個限制：看不到舊程式
- 第一版的成績單：哪些欄位準、哪些不準
- 上線後的第一個意外：網站顯示的不是網站（動手做）

### 場景 1：一條每天自己跑的管線

【畫面：阿拉蕾舉著平板，投影出一條由左到右的流程圖】

**阿拉蕾**【表情：平板展示】
盤點完現況，我提出的架構是這樣的。不用懂程式，看流程就好：

```
每天自動啟動（GitHub Actions 排程）
  ① 蒐集：TWCERT、資安院 NICS、iThome 資安日報、TechNews 四個來源
  ② 去重：同一個網址只留一筆
  ③ 評估：從內文抓出 CVE 編號，去查公開資料，填好弱點五欄
  ④ 儲存：每月一個資料檔，存在 GitHub repo，每次變更都有紀錄
  ⑤ 產出：每月 Excel、年度 Excel、查詢網站
  ⑥ 發佈：自動發佈到 GitHub Pages（免費的網站空間）
```

**Allan**【表情：思考】
我原本以為這種需求一定要用 n8n 之類的工作流程平台來串。

**阿拉蕾**【表情：眨眼比讚】
這次不用。資料都是公開的、流程是直線的，我直接寫程式，交給 GitHub 每天執行就好。

**Allan**【表情：正經】
這個選擇的代價，我們第 4 集再算。

> **📋 ISMS 旁註｜資料存在哪裡、誰能改**
> 每月一個 JSON 資料檔放在 repo 裡，所有新增、修改都有版本紀錄：誰、何時、改了什麼。
> 稽核時要佐證「這筆情資何時進來、後來有沒有被改過」，翻 GitHub 的歷史紀錄即可。

### 場景 3：阿拉蕾的第一個坦白

【畫面：阿拉蕾抓頭，頭上一個問號；背景是 Allan 的筆電，上面一支被鎖起來的 bat 檔】

**阿拉蕾**【表情：疑問抓頭】
老師，我要先坦白一件事。

**Allan**【表情：思考】
說。

**阿拉蕾**【表情：疑問抓頭】
您原本產生情資的那支 bat 程式在您自己的電腦上，**我看不到**。我在雲端的工作環境，只碰得到這個 repo 和公開網路。

**阿拉蕾**【表情：攤手說明】
所以舊表的「威脅程度」「因應對策」是用什麼規則判斷的，我只能**從三年的資料反推**：什麼樣的情資被標成高、什麼樣的被寫成「持續觀察」。

**Allan**【表情：抓頭】
那就是用猜的。

**阿拉蕾**【表情：流淚】
用「有根據地猜」……但確實繞了一段路。

> **💡 這是教學重點：AI 看不到的地方**
> AI 只能根據你給它的東西工作。它看不到你電腦上的檔案、你腦中的規則、你同事口頭約定的慣例。
> 這不是 AI 不夠聰明，而是**交代時漏了素材**。如果一開始就提供舊程式或規則文件，這段路可以少繞很多。下一集，Allan 會補上規則文件，但他會說一句出人意料的話。

**Allan**【表情：正經】

**阿拉蕾**【表情：平板展示】
我拿 **2026 年 11 月的 110 筆**情資，用新系統重新判定一次，再跟原本 Google Sheet 裡人工填的結果逐欄比對：

| 欄位 | 與原表一致的比例 | 燈號 |
|---|---|---|
| 威脅情報類別 | 93% | 🟢 |
| 弱點五欄 | 85–90% | 🟡 |
| 因應對策 | 58% | 🔴 |
| 對組織的現況威脅程度 | 45% | 🔴 |

**Allan**【表情：驚訝】
威脅程度只有四成五？

**阿拉蕾**【表情：流淚】
是……

**Allan**【表情：思考】
不過我很高興妳把數字攤開來。如果妳只跟我說「做好了」，我根本不知道哪些能信、哪些不能信。

**阿拉蕾**【表情：握拳加油】
這就是習慣二：每個階段都說清楚**驗證了什麼、沒驗證什麼**。這次我驗證了「跟舊結果像不像」，還沒驗證「到底對不對」。

**Allan**【表情：豎指頭】
這兩件事不一樣。「跟以前一樣」不等於「正確」。下一集我們處理這個。

> **💡 Allan 為什麼這樣說**
> 「回測」是拿舊的結果當對照組，是最便宜的第一道檢查。但舊結果也是人填的，也可能錯。
> Allan 刻意區分「像不像」和「對不對」，因為驗收標準是後者。這個區分，決定了下一集的走向。

> **📋 ISMS 旁註｜上線前驗收**
> 回測相當於系統上線前的驗收測試。稽核員可以觀察：驗收有沒有量化結果？未達標的項目有沒有被記錄、追蹤，而不是被略過？

### 場景 5：合併上線，然後……網站呢？

【畫面：Allan 在 GitHub 的 PR 頁面按下綠色的 Merge 按鈕，時間 18:30】

**Allan**【表情：微笑】
傍晚六點半，我合併了第一個 PR，系統正式上線。打開網站——

【畫面：瀏覽器打開 `allanloplus.github.io/intelligence/`，畫面上只有一份 README 說明文件】

**Allan**【表情：驚訝】
……這是 README 吧？我的查詢網站呢？

**阿拉蕾**【表情：疑問抓頭】
程式沒問題，是 GitHub Pages 的設定。網站的來源選成了「Deploy from a branch」，所以 GitHub 直接把 repo 首頁的說明檔當成網站。

**阿拉蕾**【表情：攤手說明】
要改成「GitHub Actions」，讓每天的排程產生網站後再發佈。

**Allan**【表情：抓頭】
這個設定只有我能改吧？

**阿拉蕾**【表情：眨眼比讚】
對，是 repo 的設定頁，要您動手。改完之後，網站就正常了！

【畫面：修正後的情資網站「情資明細與下載」頁，網址 allanloplus.github.io/intelligence（截圖 14）】

> **🛠 動手做｜合併 PR 並發佈網站**
> 1. **合併 PR**：GitHub repo → Pull requests → 點開 AI 提出的 PR → 看過「Files changed」→ 按 **Merge pull request** → **Confirm merge**。
> 2. **設定 Pages 來源**：repo 上方 **Settings**（這是 repo 的 Settings，不是個人帳號的）→ 左側 **Pages** → Build and deployment 的 **Source** 選 **GitHub Actions**。
>    ⚠ 預設可能是「Deploy from a branch」，網站會顯示 README，這正是本集遇到的狀況。
> 3. **手動執行一次**：repo 上方 **Actions** → 左側選「**情資自動更新**」→ 右側 **Run workflow** → 選 `main` → 綠色 **Run workflow**。
> 4. **確認結果**：執行完成（綠色勾勾）後，網站網址會顯示在該次執行的頁面上。本個案為 `https://allanloplus.github.io/intelligence/`。
>

### 本集一句話

> **「做出來」不等於「做對」。**
> 每個階段都要問 AI：你驗證了什麼？沒驗證什麼？
> 而「跟以前一樣」也不等於「正確」。

### 課後思考

1. 你的自動化需求裡，有沒有規則只存在某個人的電腦、某份舊文件、或某個人的腦中？交代時有沒有一起給？
2. 如果你要驗收一個系統，你會拿什麼當「對照組」？那個對照組本身可信嗎？
